# Tauridium 1.0.0 release validation

This first major release incorporates the reviewed security-hardening work since
0.9.5. It does not assert perfect security or erase upstream advisory assessments.
Final executed gates, release identities, artifact checksums and any unavailable
platform checks belong in the accompanying external
`tauridium-1.0.0-RELEASE-VALIDATION.md` handoff, not in raw public build logs.

## Compatibility and upgrade notes

Existing application identity, profile paths, service sessions, workspaces and
settings remain unchanged. Back up important data before upgrading. Personal
executable recipes now require explicit trust. Remembered credentials use the
native operating-system vault; a missing or locked vault is not permission to
retain a plaintext fallback. Follow the displayed credential/trust prompts rather
than deleting the profile or weakening the security policy.

Release tooling deliberately rejects previously tolerated unsafe inputs: dirty or
untagged source packaging, producer-local Git configuration/history, ambiguous
source roots, incomplete archive streams, unreviewed evidence and stale or modified
Flatpak candidates. Build unsigned local binaries without supplying signing keys.
Use the documented protected workflow for signed updater publication.

## Required release gates

- Clean exact release commit, pinned formatting, warnings-as-errors native,
  Flatpak and Nix compiler matrices, frontend checks and complete regression tests.
- Actual optimized native production build; fresh online npm and both Rust-lock
  advisory checks, with existing exact, expiring assessments kept visible.
- Deterministic source/runtime/documentation ZIPs from the annotated version tag;
  full decoded artifact and approved Git-history inspection with real scanner
  controls, and independent reproduction of all three ZIP hashes.
- Nix source-built package and install checks; exact committed Flatpak snapshot
  build/export, current-candidate headless test and offline policy/metadata lint.
- Synthetic-profile production GUI checks, without accessing real accounts,
  owner credentials or installed application data.

## Platform and publication boundaries

Linux execution and Windows GNU cross-checks do not establish native Windows
MSVC, vault, DACL, pipe, WebView2 GUI or Scoop acceptance. Native Windows CI and
manual acceptance remain necessary before platform-wide public release clearance.
macOS is best-effort and is not represented as locally tested.

The builder retains a precisely reviewed macOS-only RSA advisory assessment;
maintenance notices and low-severity workflow syntax recommendations are documented
in `docs/SECURE-RELEASES.md` and the private closeout. No audit ignore or reduced
severity threshold replaces these assessments.

Publishing requires verified owner-configured environments and signing-key scope,
successful required platform/security jobs, version-bound signatures and remote
draft-byte verification. A local annotated tag is not proof of public publication
or updater signatures. The Flatpak publication reference is pinned after the
release commit/tag to avoid a self-referential commit; local candidate checks do
not constitute online Flathub approval.
